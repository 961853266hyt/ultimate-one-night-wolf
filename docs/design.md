# 一夜狼 · 后端系统设计

> 技术栈：FastAPI + Pydantic v2 + 原生 WebSocket，前端 React。最后更新：2026-09-30
> 进度：M1 规则引擎已完成，代码在 `server/app/domain/`。

## 0. 一页总结

- **三层结构**：Gateway（FastAPI，只管收发和鉴权）→ RoomActor（每个房间一个 asyncio 任务）→ Domain（纯 Python 写的房间和游戏规则）
- **每个房间一个 actor**：这个房间的所有指令和倒计时都进同一个收件箱，按顺序处理。不用锁，也没有全局时钟；一个房间出错不影响其他房间
- **服务端权威**：客户端只发送意图。服务端给每个人推送**他自己能看到的**完整视图，而且只在视图变化时才推
- **状态放在内存**：进行中的对局不落库。P1 再把已结束的对局写进 SQLite，用来复盘和查战绩
- **一个容器**：FastAPI 同时托管前端静态文件，只开一个 worker

## 1. 需求

**功能**

- 开房后得到一个 4 位房间号，把链接或房间号发给别人，他们就能进房
- 大厅：房主配置牌堆和各阶段时长，可以踢人、开局。房主离开时，房主身份自动转给别人
- 一局的流程：发牌看牌 → 夜晚逐个角色行动 → 白天讨论 → 同时投票 → 揭晓（公开所有牌和夜间完整记录）
- 再来一局：回到大厅，人员和配置都保留
- 刷新、切到后台、断网回来之后，都能回到原来的座位和进度

**非功能需求，按优先级排**

1. 信息不泄露：任何人都不能从网络流量或页面数据里推断出别人的身份
2. 扛得住手机断线：在手机上，断线是常态，不是异常
3. 简单：一个人就能看懂、能维护
4. 性能：够用即可，每个阶段都是按秒计的

**默认假设**（如果不对，随时可以改）

- 大家面对面玩，或者开着外部语音，所以 v1 不做聊天
- 使用官方基础版角色。化身幽灵放到 v1.1，但接口从第一天起就给它留好了位置
- 不做注册，用访客身份
- 规模：同时在线的房间不超过几百个，单实例部署

## 2. 架构

```
Browser (React)
   │ HTTP  /api/*               建身份、开房、查询
   │ WS    /ws/rooms/{code}     进房之后的一切
   ▼
① Gateway · FastAPI
   路由、鉴权、Pydantic 校验。不包含任何游戏规则
   │ 投递指令                          ▲ 视图帧（只发给视图变了的人）
   ▼                                   │
② RoomActor · 每个房间一个 asyncio 任务
   收件箱串行处理 · 自带倒计时 · 连接表 · 渲染并推送
   │ 同步调用
   ▼
③ Domain · 纯 Python
   Room（大厅）· Game（状态机）· 角色注册表 · 计票与胜负 · 视图投影

旁路（P1）：Recorder 任务 ──▶ SQLite（只写已结束的对局）
```

依赖只能往下走：api → runtime → domain。domain 不 import 任何其他层，所以整套规则不用启动服务器就能测试。

## 3. 领域模型

### 3.1 身份、房间、牌

- **访客身份**：第一次打开页面时调用 `POST /api/session`，拿到 `player_id` 和签名 token，存进 localStorage。token 用 HMAC 签名，服务端不需要保存；服务器重启后身份依然有效
- **Room**：包括房间号、成员（id、昵称、是否在线）、房主、配置（牌堆、各阶段时长），以及当前这局 Game（在大厅里为空）。开房的人直接成为成员和房主，连上来之后才算在线
- **牌堆**：房主没有自定义时，按人数自动推荐（前 n + 3 张：狼 ×2、预言家、强盗、捣蛋鬼、村民、酒鬼、失眠者、爪牙、皮匠、猎人、村民、村民）。守夜人要成对才好玩，所以只在自定义配牌里出现
- **Slot**：放牌的位置。玩家的 slot 就是他的 `player_id`，三张底牌分别是 `C0`、`C1`、`C2`。所有看牌、换牌的目标都用 slot 表示，所以夜间动作只有一种格式：`targets: [slot, ...]`
- **牌堆构成是公开的**：和桌游一样，大家都知道这局有哪些角色，只是不知道谁是谁

### 3.2 状态机

```
lobby ──start──▶ deal ──▶ night[1..k] ──▶ day ──▶ vote ──▶ reveal ──rematch──▶ lobby
```

| 阶段 | 默认时长 | 什么时候结束 | 玩家能做什么 |
|---|---|---|---|
| lobby | — | 房主开局（3–10 人，且全员在线） | 进出房间；房主配牌、踢人 |
| deal | 10s | 全员点「看好了」，或者超时 | 看自己的牌 |
| night × k | 每步 12s | **只看时间，从不提前结束** | 轮到的角色行动 |
| day | 5min | 超时，或者全员点「可以投票」 | 讨论 |
| vote | 60s | 全员投完，或者超时 | 投给另一名玩家，一人一票，投出后不能改 |
| reveal | — | 房主点「再来一局」 | 查看揭晓结果和夜间记录；新的人可以在这时加入 |

k 是牌堆里**会在夜里醒来的角色种数**。牌堆是公开的，所以直接跳过不在牌堆里的角色，不会泄露任何信息。

时间和随机数都由调用方作为参数传入：`room.handle(player, cmd, now, rng)`、`room.tick(now, rng)`。domain 自己不读时钟，所以测试可以精确控制时间。运行时在 `room.next_deadline()` 这个时间点调用 `tick`；每次 tick 之后，下一个截止时间一定在未来，运行时不会空转。

### 3.3 角色

每个角色一个文件，继承同一个基类，然后注册到 `ROLES`：

```python
class Role:
    id: ClassVar[RoleId]
    team: ClassVar[Team] = Team.VILLAGE   # 胜负按夜里换牌结束后手上的牌来算
    night_order: ClassVar[int | None]     # None 表示夜里不醒
    max_copies: ClassVar[int] = 1

    def wake_info(self, table, me) -> list[Knowledge]    # 一醒来就知道的：狼互认、爪牙看狼、失眠者看自己
    def prompt(self, table, me) -> Prompt | None         # 此刻能选什么；每次行动后都会重新求值，默认每步只能行动一次
    def choices(self, table, me) -> Prompt | None        # 普通角色只需要覆盖这个
    def act(self, table, me, targets) -> list[Knowledge] # 换牌，返回看到的内容；targets 已经按 prompt 校验过
```

角色拿到的是 `Table`（牌桌）接口，只包含它们需要的东西：玩家、牌、这一步谁行动过、`players_acting_as()`、`swap()`。`Game` 实现了这个接口，但角色不依赖 `Game`。

目标是否合法由引擎统一对照 Prompt 校验，角色不用自己写校验。Prompt 标了 `required` 的选择（目前只有酒鬼），超时后由引擎随机代选一个合法目标，角色也不用写超时逻辑。

`Prompt` 描述玩家「能选什么」，前端用**一个通用的目标选择器**来渲染。新加的角色只要选择方式能用 Prompt 描述，前端就不用写新代码：

| 角色 | 顺序 | 能做什么 / 醒来得到的信息 | 超时 |
|---|---|---|---|
| 狼人 ×2 | 2 | 互相认识；独狼可以看 1 张底牌 | 放弃 |
| 爪牙 | 3 | 看到所有狼（狼看不到他） | — |
| 守夜人 ×2 | 4 | 互相认识 | — |
| 预言家 | 5 | 看 1 名其他玩家的牌，**或者**看 2 张底牌 | 放弃 |
| 强盗 | 6 | 和 1 名其他玩家换牌，然后看自己的新牌 | 放弃 |
| 捣蛋鬼 | 7 | 交换另外 2 名玩家的牌，不看 | 放弃 |
| 酒鬼 | 8 | 和 1 张底牌交换，不看（必须做） | **系统随机代选** |
| 失眠者 | 9 | 看自己现在的牌 | — |
| 猎人 / 皮匠 / 村民 ×3 | — | 夜里不醒 | — |

**化身幽灵（v1.1）** 在接口里已经留好了位置：

- `acting_role(player)` 默认返回发到的牌；化身幽灵复制之后，返回他复制来的角色。谁在哪一步醒来，都按这个函数算
- `prompt()` 在每次行动之后都会重新求值。普通角色行动过一次，就返回 None；化身幽灵复制了预言家之后，会返回预言家的 Prompt，于是他可以接着验人
- 牌堆里同时有失眠者时，夜间计划要多加一步「化身失眠者」。**不管他复制了什么，这一步都要走**，否则会泄露信息

### 3.4 夜晚

1. 进入一步时：找出这一步醒来的人，把醒来即得的信息发给他们，并给能行动的人挂上 Prompt
2. 收到 `night_action` 时：先校验（是不是这一步、是不是轮到你、有没有行动过、目标合不合法），然后立即结算（换牌，并记下看到的东西），结果只推给他本人
3. 时间到了：Prompt 标了 `required` 却没行动的人，由系统随机代选，然后进入下一步。夜间记录里会标明这是代选的

**看到的信息在行动那一刻就记录下来**，之后牌再怎么被换都不会改变它。玩家整局看到的「我的牌」都是发到的那张；想知道自己现在手里是什么，只能靠失眠者这类角色。

### 3.5 投票与胜负

- 得票最多且至少有 2 票的玩家出局，平票就一起出局；如果没有人超过 1 票，就没有人出局
- 出局的玩家如果手里是猎人，他投的那个人也一起出局（可以连锁）
- 胜负按官方规则判定，包括皮匠、爪牙、狼全在底牌这些分支。这些规则全部放在 `rules.py` 里，用表驱动测试逐条覆盖

## 4. 运行时：RoomActor

```python
async def run(self):
    while True:
        msg = await self.next_message()      # 最多等到 room.next_deadline，到点就返回一个 Tick
        draft = self.room.model_copy(deep=True)
        try:
            draft.apply(msg, now=clock())    # 处理玩家指令或 Tick
            self.room = draft                # 成功了才替换：天然就是事务
        except RuleError as e:
            self.reply(msg, error=e.code)    # 指令不合法：状态保持不变
        except Exception:
            log.exception(...)               # 代码 bug：只影响这一条指令、这一个房间
            self.reply(msg, error="INTERNAL")
        self.publish()                       # 渲染视图，只把变了的放进发送队列
```

- **串行**：一个房间同一时刻只处理一条指令，所以不需要锁
- **事务**：状态只有几 KB，每条指令都先在副本上执行，出错了就当没发生过
- **倒计时**：每个房间自己算下一个截止时间，没有全局轮询
- **推送**（`publish`）：给每个在线的人渲染视图，和上次发给他的比较，**只发变了的**。`seq` 是每人一个的计数器。actor 只负责把帧放进连接的发送队列，从不等待网络；队列里还没发出去的旧快照会被新快照直接覆盖
- **新连接**：不管视图有没有变，都先补发一帧当前快照
- **回收**：连续 10 分钟没有人在线，actor 自己退出，manager 删掉这个房间。全局房间数有上限

## 5. 接口

### 5.1 HTTP

| 接口 | 用途 |
|---|---|
| `POST /api/session` | 获取访客身份 `{player_id, token}`；带着有效 token 调用时原样返回 |
| `POST /api/rooms` | 开房，请求体 `{name}`，返回 `{code}`；调用者直接成为成员和房主 |
| `GET /api/rooms/{code}` | 进房前预览：当前阶段、人数、能否加入 |
| `GET /api/roles` | 角色目录：名字、阵营、说明、张数上限（给配牌界面用） |
| `GET /api/me/games` | P1：我的战绩 |
| `GET /healthz` | 健康检查 |

### 5.2 WebSocket `/ws/rooms/{code}`

进房、重连、刷新都走同一条路：连上之后发一条 `hello`。

| 客户端 → 服务端 | 字段 | 什么时候发 |
|---|---|---|
| `hello` | token, name | 首帧。还不是成员就加入，已经是成员就恢复 |
| `configure` | settings（deck、timings） | 房主，大厅中。整份替换；deck 为 null 表示自动推荐 |
| `kick` | player | 房主，大厅中 |
| `start` | — | 房主，大厅中 |
| `leave` | — | 在大厅里直接移出；对局中视为离线，座位保留到这局结束 |
| `confirm_card` | — | deal 阶段 |
| `night_action` | targets | 轮到你时 |
| `ready_to_vote` | — | day 阶段 |
| `vote` | target | vote 阶段 |
| `rematch` | — | 房主，reveal 阶段 |

| 服务端 → 客户端 | 字段 | 什么时候发 |
|---|---|---|
| `state` | seq, server_now, view | 只在你的视图变化时 |
| `error` | code, ref? | 只发给出错的人；`ref` 对应请求里的 id |

所有消息都是按 `type` 区分的 Pydantic 判别联合。用脚本导出 JSON Schema，再生成 `frontend/src/api/types.gen.ts`，前后端的类型就不用手工同步。

### 5.3 一帧 state 长什么样

夜里轮到预言家，他还没行动：

```jsonc
{
  "type": "state",
  "seq": 17,                             // 每人独立递增，客户端丢弃旧帧
  "server_now": 1790000003400,           // 客户端用它校正本机时钟
  "view": {                              // domain/views.py 里的 PlayerView
    "phase": "night",
    "ends_at": 1790000012000,            // 毫秒时间戳
    "room": {
      "code": "KXQB",
      "host": "p_7f3a",
      "members": [{ "id": "p_7f3a", "name": "阿胡", "online": true, "seat": 0 }],   // 其余成员略
      "deck": ["werewolf", "werewolf", "seer", "robber", "troublemaker", "villager", "drunk"],
      "auto_deck": true,
      "timings": { "deal": 10, "night_step": 12, "day": 300, "vote": 60 }
    },
    "me": {
      "id": "p_7f3a",
      "seat": 0,
      "card": "seer",                    // 永远是发到的那张
      "knowledge": []                    // 验人之后多一条 { "type": "saw_card", "step": "seer", "slot": "p_19bc", "role": "robber" }
    },
    "prompt": { "options": [{ "kind": "player", "count": 1 }, { "kind": "center", "count": 2 }], "required": false },
    "night": { "step": "seer", "index": 2, "total": 5 },
    "deal": null, "day": null, "vote": null, "result": null
  }
}
```

每个阶段只有自己那一块有值：

| 字段 | 内容 |
|---|---|
| `deal` | `confirmed`：已经看好牌的人 |
| `night` | `step`、`index`（从 1 开始）、`total` |
| `day` | `ready`：已经同意投票的人 |
| `vote` | `voted`：已经投了的人；`mine`：我投给了谁。不含别人投给了谁 |
| `result` | 发牌时和最终的所有牌、每个人夜里得到的信息、夜间记录、票型、出局者、获胜阵营、赢家 |

## 6. 防泄露

这是隐藏身份游戏的根本。一共四条信道，每一条都要堵住：

| 信道 | 规则 |
|---|---|
| 内容 | 视图是字段显式列出的 Pydantic 模型，没写进去的字段不可能出现。揭晓之前，任何人的视图里都看不到别人的牌、别人看到了什么、别人投给了谁 |
| 时长 | 夜间每一步的时长都固定，和这个角色在不在玩家手里、有没有行动都无关。只有公开信息才能让阶段提前结束：全员看好牌、全员同意投票、全员投完 |
| 流量 | 只给视图变了的人发帧，`seq` 每人独立计数。私密的变化（比如夜间行动）只推给本人，错误只回给发送者，任何人都看不出「有人刚行动了」 |
| 线下动作 | 面对面玩时，夜里如果只有一个人在点手机，就等于亮了身份。所以前端让所有人每一步都有东西可点（诱饵操作，纯前端实现，不发给服务器） |

另外还有两条：发牌和房间号都用 `secrets` 生成，不用可预测的伪随机数；日志里不记录 token，也不记录私密视图。

## 7. 断线与异常

| 场景 | 处理方式 |
|---|---|
| 刷新、切到后台、断网后回来 | 自动重连并发送 `hello`，收到完整快照，回到原位 |
| 夜里轮到你时掉线 | 这一步照常走满；超时后大多数角色视为放弃，酒鬼则随机替他换 |
| 投票时掉线 | 这一票不计；其他人投完后不等他，最多等到超时 |
| 在大厅里掉线 | 显示为离线，2 分钟后自动移出 |
| 房主掉线 | 30 秒后，房主身份转给下一个在线的成员 |
| 所有人都离开 | 10 分钟后销毁房间 |
| 某个房间的代码出错 | 这条指令回滚并报 `INTERNAL`，其他房间不受影响 |
| 服务器重启 | 所有房间丢失，前端收到 `ROOM_NOT_FOUND` 后回到首页；访客身份仍然有效 |

## 8. 持久化（P1）

对局进行中只存在于内存里。进入 reveal 阶段时生成一份 `GameRecord`，交给后台的 Recorder 任务写进 SQLite。写入失败只记日志，永远不会阻塞房间。

| 表 | 字段 |
|---|---|
| `games` | id, room_code, started_at, ended_at, settings (JSON), record (JSON：发牌、最终的牌、夜间记录、票型、结果) |
| `game_players` | game_id, player_id, seat, name, dealt_role, final_role, died, won（按 player_id 建索引，用来查战绩） |

`record` 里有完整的夜间记录，可以直接用来渲染复盘。以后如果要多实例部署，就换成 Postgres。

## 9. 部署与规模

- 用一个 Docker 镜像：先构建前端，把 `dist/` 复制进后端镜像，由 FastAPI 托管静态文件（前端路由全部回退到 `index.html`）。只有一个端口，前后端同源，不需要 CORS
- 用 `uvicorn --workers 1` 启动。房间状态在进程内存里，开多个 worker 会把同一个房间的人分到不同进程。这是硬约束
- 需要一台能跑常驻进程和 WebSocket 的机器，比如 VPS，或者 Fly.io、Railway 这类平台
- 上限：WebSocket 单条消息不超过 4KB；每条连接每秒最多 20 条消息；按 IP 对开房和进房失败限流；全局房间数有上限
- 发布新版本会中断正在进行的对局。所以收到 SIGTERM 后先停止开新房，等进行中的对局结束（最多等 10 分钟）再退出

**容量估算**：一局大约 8 分钟，最多 10 人，每人每次收到的快照是 1–2KB。单个进程跑几百个房间，CPU 和带宽都很空闲。

**什么时候需要改**：真的需要多台机器时，按房间号把请求路由到固定的实例（可以把实例编号编进房间号，也可以让网关查一张映射表），状态仍然留在进程内。不要把状态搬进 Redis 再加分布式锁。

## 10. 测试

- **domain 层**（绝大部分测试都在这里）：每个角色都有表驱动测试；胜负规则逐条覆盖；用固定的随机源，脚本化地打完整局
- **性质测试**（hypothesis）：用随机牌堆加随机的合法操作打完整局，断言三件事：牌的总数和种类守恒；揭晓之前任何视图都不包含别人的牌；有人夜间行动时，其他人收到 0 帧
- **api 层**：用 TestClient 走真实的 WebSocket，覆盖进房、重连和完整的一局
- **契约**：CI 里重新生成 TS 类型，前端能编译通过，就说明前后端类型没有漂移

## 11. 关键取舍

| 决定 | 选择 | 为什么 | 放弃了什么 |
|---|---|---|---|
| 并发模型 | 每个房间一个 actor | 天然串行，不用锁；自带定时器；错误互相隔离 | 要写一个收件箱循环（约 50 行） |
| 同步方式 | 按人推送全量快照 | 幂等，重连不需要任何特殊逻辑 | 多用一点带宽，可以忽略 |
| 夜间节奏 | 按顺序逐个唤醒，每步定长 | 和官方 App 一致，防泄露也容易分析 | 夜晚时间更长。「全员同时操作、服务端按顺序结算」会更快，但强盗、失眠者要等到夜晚结束才能看到结果，而且化身幽灵很难写对 |
| 状态存储 | 进程内存 | 最简单，一局只有几分钟 | 重启会丢失对局，也不能直接水平扩展 |
| 身份 | 签名的访客 token | 零门槛，天然支持再来一局和战绩 | 不能跨设备；以后需要时再加登录 |
| 角色规则 | 一个角色一个文件 + 注册表 | 加角色不用改其他文件，前端复用同一个选择器 | 角色之间的关联要通过 `Game` 上的查询函数来表达 |
| 传输 | 原生 WebSocket | FastAPI 自带；重连问题已经由全量快照解决 | 用不上 Socket.IO 的房间、降级这些功能 |

## 12. 里程碑

1. **M1 规则引擎** ✅：domain 层全部完成（化身幽灵除外），包括大厅规则（配牌、踢人、再来一局、房主转交、离线移出）。全部用纯单测覆盖，性质测试随机打完整局，不需要网络
2. **M2 联机**：actor、WebSocket 加上最简单的前端，能用几台手机真打一局
3. **M3 可以上线**：大厅和断线重连的前端体验、部署
4. **M4 扩展**：对局记录和战绩、化身幽灵、观战

## 13. 和旧项目的区别

| 旧项目 | 新设计 |
|---|---|
| 一个房间的逻辑分散在 room / phases / protocol / hub 四个模块里 | 运行时逻辑都在 RoomActor 里，规则在 domain 的纯数据 Room / Game 里 |
| 全局 250ms 轮询 + 每个房间一把锁；一个房间抛异常，全服就停摆 | 每个房间一个 actor，自带定时器，出错只影响自己 |
| 手写 JSON 标签表和解码器，TS 类型靠手工同步 | Pydantic 判别联合自动校验，TS 类型自动生成 |
| 引擎只认座位号，外面还要包一层 player_id ↔ 座位的翻译 | 直接用 player_id；底牌用 C0–C2，两者统称 slot |
| 夜间规则全写在一个大的 match 里 | 每个角色一个文件；前端用一个通用的目标选择器 |
| 每个房间、每个座位各有一个 token | 每个浏览器一个访客身份 |
| 任何消息都广播给全员（存在流量侧信道） | 只发给视图变了的人 |
| 夜晚固定走 8 步 | 只走牌堆里有的角色 |
